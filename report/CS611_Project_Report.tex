\section{Introduction}

The Minimum Spanning Tree (MST) problem is one of the most fundamental problems in graph theory [1]. Given a connected, undirected, weighted graph $G = (V, E, w)$, the objective is to find a spanning tree $T \subseteq E$ with minimum total edge weight [1]. MST algorithms are essential in network design, VLSI routing, cluster analysis, and approximation algorithms for NP-hard problems [1].

As real-world graphs scale to millions of vertices [9], classical sequential algorithms such as Kruskal's [2] cannot exploit multi-core hardware [4]. This has motivated research on parallel MST algorithms based on Bor\r{u}vka's algorithm [3], which achieves real speedup through per-component independence [4,5,6]. However, naive implementations of Bor\r{u}vka's in interpreted languages suffer from two critical bottlenecks: repeated full-edge scans without graph contraction, and interpreter overhead in hot loops [4,6].

This project addresses both bottlenecks. We implement Kruskal's [2] and Bor\r{u}vka's [3] algorithms in two configurations: a baseline Python implementation and an optimized version using Numba JIT compilation with proper graph contraction [4]. We evaluate both on two SNAP benchmark datasets [9] in the domain of \textbf{road networks} (roadNet-CA, 1.96M nodes) and \textbf{e-commerce networks} (amazon0302, 262K nodes). The optimized Bor\r{u}vka implementation processes the full Amazon dataset in 0.08 seconds, compared to being infeasible in the unoptimized version.

Section~2 reviews the literature. Section~3 analyzes both algorithms and the role of graph contraction. Section~4 describes the SNAP datasets and implementation. Section~5 presents results showing that proper contraction and JIT compilation transform Bor\r{u}vka from 6.6$\times$ slower than Kruskal to competitive or faster. Section~6 concludes.

\section{Literature Review}

\subsection{Classical Sequential Algorithms}

Kruskal's algorithm [2] sorts all edges and greedily adds the lightest non-cycle-forming edge using Union-Find with path compression and union by rank [1]. Its complexity is $O(E \log E)$ [1]. Prim's algorithm achieves $O(E + V \log V)$ with Fibonacci heaps but is inherently serial [1]. Both are proven correct by the cut property [1].

\subsection{Parallel Algorithms Based on Bor\r{u}vka}

Bor\r{u}vka's algorithm [3] operates in rounds where every component independently selects its minimum-weight outgoing edge [1]. The component count halves each round, yielding $O(\log V)$ rounds [1]. The find-minimum phase is embarrassingly parallel [4]. Durbhakula [4] achieved 2.03$\times$ speedup on 6 C++ cores. Schimek et al.\ [5] scaled to 65,536 cores (800$\times$). Bhargava and Zaia [6] achieved 13.3$\times$ on CPU and 29$\times$ on GPU. Fallin et al.\ [8] presented state-of-the-art GPU MST at SC '23. Dhouib [7] proposed DM-MSTP, a matrix-based $O(V^2)$ method for dense graphs.

\subsection{The Contraction Optimization}

A critical implementation detail noted by Durbhakula [4] and Bhargava and Zaia [6] is that Bor\r{u}vka's algorithm must perform \textbf{physical graph contraction} after each round: internal edges (both endpoints in the same component) are removed, and multi-edges between components are reduced to the lightest [4]. Without contraction, the algorithm scans all $E$ original edges in every round, multiplying the work by $O(\log V)$ [4]. With contraction, the edge set shrinks exponentially, making Bor\r{u}vka competitive with Kruskal even sequentially [4,6].

\section{Algorithm Design and Analysis}

\subsection{Kruskal's Algorithm}

Kruskal's sorts $E$ edges in $O(E \log E)$, then scans once with $O(\alpha(V))$ Union-Find per edge [1,2]. Total: $O(E \log E)$ [1]. Its sort-once-scan-once structure makes it fast sequentially, but the global sort is inherently serial [4].

\begin{algorithm}[H]
\caption{Kruskal's MST (Sequential) [2]}
\begin{algorithmic}[1]
\Require Connected graph $G = (V, E, w)$
\Ensure MST edge set $T$, total weight $W$
\State Sort $E$ by weight $w$ in non-decreasing order
\State Initialize Union-Find $\mathcal{U}$ over $V$ with path compression and union by rank
\State $T \gets \emptyset$,\; $W \gets 0$
\For{each edge $(u, v, w)$ in sorted order}
    \If{$\mathcal{U}.\textsc{Find}(u) \neq \mathcal{U}.\textsc{Find}(v)$}
        \State $\mathcal{U}.\textsc{Union}(u, v)$
        \State $T \gets T \cup \{(u,v)\}$,\; $W \gets W + w$
    \EndIf
    \If{$|T| = |V| - 1$} \textbf{break} \EndIf
\EndFor
\State \Return $T, W$
\end{algorithmic}
\end{algorithm}

\subsection{Bor\r{u}vka's Algorithm with Contraction}

Each round: (1) find minimum outgoing edge per component (parallel) [4]; (2) add selected edges to MST; (3) merge components and contract the graph [4]. With contraction, the edge count decreases by at least half each round [4,6]. Sequential complexity: $O(E \log V)$ [1]. Parallel complexity with $p$ threads: $O(E/p \cdot \log V)$ ideal [4].

\begin{algorithm}[H]
\caption{Bor\r{u}vka's MST (Sequential, with Graph Contraction) [3,4]}
\begin{algorithmic}[1]
\Require Connected graph $G = (V, E, w)$
\Ensure MST edge set $T$, total weight $W$
\State Initialize Union-Find $\mathcal{U}$ over $V$
\State $T \gets \emptyset$,\; $W \gets 0$
\While{number of components $> 1$}
    \For{each component $C$}
        \State $\text{cheapest}[C] \gets$ lightest edge leaving $C$
    \EndFor
    \For{each component $C$ with $\text{cheapest}[C] = (u, v, w)$}
        \If{$\mathcal{U}.\textsc{Find}(u) \neq \mathcal{U}.\textsc{Find}(v)$}
            \State $\mathcal{U}.\textsc{Union}(u, v)$
            \State $T \gets T \cup \{(u,v)\}$,\; $W \gets W + w$
        \EndIf
    \EndFor
    \State \textbf{Contract:} remove all edges $(u,v)$ where $\mathcal{U}.\textsc{Find}(u) = \mathcal{U}.\textsc{Find}(v)$
\EndWhile
\State \Return $T, W$
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[H]
\caption{Bor\r{u}vka's MST (Parallel, with Graph Contraction) [3,4,6]}
\begin{algorithmic}[1]
\Require Connected graph $G = (V, E, w)$, $p$ threads
\Ensure MST edge set $T$, total weight $W$
\State Initialize Union-Find $\mathcal{U}$ over $V$
\State $T \gets \emptyset$,\; $W \gets 0$
\While{number of components $> 1$}
    \State \textbf{Parallel:} flatten component IDs via path compression \Comment{$O(V/p)$}
    \State \textbf{Parallel:} for each edge, find minimum outgoing edge per component \Comment{$O(E/p)$}
    \State \textbf{Serial:} merge selected components via Union-Find
    \State $T \gets T \cup \{\text{selected edges}\}$,\; update $W$
    \State \textbf{Parallel:} contract graph --- remove internal edges \Comment{$O(E/p)$}
\EndWhile
\State \Return $T, W$
\end{algorithmic}
\end{algorithm}

\subsection{The Role of JIT Compilation}

Python's interpreter adds overhead to every loop iteration, function call, and object allocation [4]. For graph algorithms with millions of iterations, this overhead dominates the actual computation. Numba JIT compiles Python functions to machine code via LLVM, eliminating interpreter overhead and enabling OpenMP-style parallelism through \texttt{prange} [10]. This bypasses the Global Interpreter Lock (GIL) that prevents true multi-threading in standard Python [4].

\begin{tabular}{lccl}\toprule
\textbf{Algorithm} & \textbf{Complexity} & \textbf{Parallel?} & \textbf{Contraction?} \\\midrule
Kruskal's [2] & $O(E \log E)$ & No [4] & N/A \\
Bor\r{u}vka (no contraction) & $O(E \cdot \log V)$ & Yes [4] & No (full scan each round) \\
Bor\r{u}vka (with contraction) [4] & $O(E \log V)$ & Yes [4] & Yes ($E$ shrinks per round) \\
\bottomrule
\end{tabular}
\caption{Without contraction, Bor\r{u}vka scans all $E$ edges $\log V$ times. With contraction, work decreases exponentially [4].}
\end{table}

\subsection{Two Implementation Configurations}

\textbf{Baseline (Pure Python):} Standard Python with list-based edges, dictionary-based minimum tracking, and no graph contraction. Represents the naive implementation commonly found in textbooks.

\textbf{Optimized (Numba JIT + Contraction):} All hot loops compiled to machine code via Numba \texttt{@njit} [10]. Pre-allocated NumPy arrays replace dictionaries. Bor\r{u}vka performs physical contraction after each round (internal edges filtered out). Parallel variant uses \texttt{prange} for the find-minimum phase, which releases the GIL and distributes work across CPU cores [10].

\textbf{Native (Rust + Rayon):} Native implementations using standard \texttt{Vec} structures and \texttt{rayon} for parallel data processing. Employs pattern-defeating quicksort for Kruskal and efficient work-stealing for Bor\r{u}vka.

\subsection{Experimental Configuration}

All benchmarks run on an AMD Ryzen 9 3900X (12 physical cores, 24 threads via SMT, up to 4.67\,GHz). Five experiments on SNAP subgraphs [9] with 8 graph sizes per dataset (1K to 200K nodes for road, 1K to 262K for Amazon). Each measurement repeated 5 times; we report the median with min/max error bars. Thread counts: 1, 2, 4, 6, 8, 12, 16, 24. Correctness validated against NetworkX [12]---an independent MST implementation---at all 16 graph sizes (8 road + 8 Amazon). All 16 validations passed with exact weight agreement (Figure~\ref{fig:ahmed_validation}).

\subsection{E1: Road Network Scalability}

\begin{figure}[H]\centering
\includegraphics[width=0.78\textwidth]{figures/ahmed_rust_road_scalability.png}
\caption{E1 (Rust/Rayon): Same sweep in Rust. Kruskal is fastest (0.013s at 200K) due to \texttt{sort\_unstable} (pdqsort). Bor\r{u}vka-Seq (0.017s) is slightly slower. Bor\r{u}vka-Par incurs thread-pool overhead at these sizes [2,4,11].}
\label{fig:ahmed_rust_road}
\end{figure}

RoadNet-CA is a sparse, planar graph (avg.\ degree 3.1). With Numba JIT and contraction, Bor\r{u}vka-Seq outperforms Kruskal because contraction reduces the already-sparse edge set rapidly ($\sim$17 rounds for 200K nodes). Each round eliminates $>50\%$ of edges [4]. In Rust, Kruskal's advantage returns because \texttt{sort\_unstable} (pdqsort) is $2\times$ faster than NumPy's \texttt{argsort} (introsort), and the sort-once cost dominates [11].

The Bor\r{u}vka-Par line sits above Bor\r{u}vka-Seq at all sizes because the parallel overhead (thread-pool creation, comp-ID flattening, edge-filter kernel launch) exceeds the benefit for graphs with $<300$K edges. The sequential find-minimum phase---which is inherently serial due to indexed-reduction data races---remains the bottleneck [4].

\begin{figure}[H]\centering
\includegraphics[width=0.78\textwidth]{figures/ahmed_python_amazon_scalability.png}
\caption{E2 (Python/Numba): Amazon from 1K to 262K (full dataset, 900K edges). Bor\r{u}vka-Seq (0.068s) and Bor\r{u}vka-Par (0.057s) outperform Kruskal (0.112s) at full scale. The denser graph amplifies contraction's benefit [3,9].}

\begin{figure}[H]\centering
\includegraphics[width=0.78\textwidth]{figures/ahmed_rust_amazon_scalability.png}
\caption{E2 (Rust/Rayon): Full Amazon in Rust. Kruskal (0.059s), Bor\r{u}vka-Seq (0.072s), and Bor\r{u}vka-Par (0.063s) converge at full scale [2,3,9].}

Amazon0302 has a power-law degree distribution (avg.\ degree 6.1) with high-degree hubs [9]. The denser structure means each contraction round removes more edges than in the road network, making Bor\r{u}vka competitive even sequentially. At full scale (262K nodes, 900K edges), Python/Numba Bor\r{u}vka-Par (0.057s) achieves a $1.97\times$ speedup over Kruskal (0.112s) due to the combination of contraction benefit and the parallel comp-ID flattening + edge filtering phases [4]. In the pure Python baseline, Bor\r{u}vka was skipped entirely above 50K nodes because repeated scanning of 900K edges was impractical [3].

\subsection{E3: Parallel Speedup Analysis}

\begin{figure}[H]\centering
\includegraphics[width=\textwidth]{figures/ahmed_python_parallel_speedup.png}
\caption{E3 (Python/Numba): Speedup vs.\ thread count on 12-core/24-thread Ryzen 9 3900X. Road (100K, 200K): flat at $\sim$0.7--0.8$\times$ (parallel overhead dominates sparse graph). Amazon (262K): peak 1.35$\times$ at 24 threads as denser edges amortize overhead [4,10].}
\label{fig:ahmed_py_speedup}
\end{figure}

\begin{figure}[H]\centering
\includegraphics[width=\textwidth]{figures/ahmed_rust_parallel_speedup.png}
\caption{E3 (Rust/Rayon): Peak speedup of 1.94$\times$ on road (200K, 8 threads) and 1.48$\times$ on Amazon (262K, 8 threads). Rayon's work-stealing scheduler achieves better utilization than Numba's static prange. Performance degrades beyond 12 physical cores due to SMT contention [4,11].}
\label{fig:ahmed_rust_speedup}
\end{figure}

\textbf{Python/Numba:} On the sparse road network, Bor\r{u}vka-Par is \emph{slower} than Bor\r{u}vka-Seq at all thread counts (0.7--0.8$\times$ ``speedup''). The parallel phases (\texttt{prange} for comp-ID flattening, edge filtering) process only $\sim$138K edges at 100K nodes, which is too little work to amortize Numba's OpenMP thread-fork overhead [10]. On the denser Amazon graph (900K edges), the parallel variant achieves modest 1.35$\times$ speedup at 24 threads because the larger edge set provides enough per-thread work [4,10].

\textbf{Rust/Rayon:} Rayon's work-stealing scheduler achieves substantially better results: 1.94$\times$ on road (200K nodes, 8 threads) and 1.48$\times$ on Amazon (262K, 8 threads). The superior scaling comes from three factors: (1) Rayon uses adaptive task granularity rather than fixed-chunk \texttt{prange} [11], (2) no GIL-equivalent contention, and (3) lower per-thread overhead ($\sim\mu$s vs.\ $\sim$ms for Numba) [11]. Beyond 12 physical cores, SMT threads share execution units, causing the $>$16-thread degradation visible in Figure~\ref{fig:ahmed_rust_speedup}.

\textbf{Amdahl's Law Analysis:} Our parallel Bor\r{u}vka has a large serial fraction $f$: the find-minimum phase and merge phase are both sequential. Using Amdahl's formula $S = 1/(f + (1-f)/p)$, the observed 1.94$\times$ peak speedup at $p=8$ implies $f \approx 0.44$, meaning $\sim$56\% of the work is parallelizable (comp-ID flattening + edge filtering). This explains why speedup saturates well below the 12-core physical limit [4,6].

\subsection{E4: Parallel Efficiency}

\begin{figure}[H]\centering

The MST weights match exactly across both languages at all 16 sizes (Table~\ref{tab:perf}), confirming correctness of the unified LCG PRNG seeding strategy.

\section{Conclusion}

This project evaluated Kruskal's [2] and Bor\r{u}vka's [3] algorithms on two SNAP benchmark datasets [9] (roadNet-CA and amazon0302), implemented in Python (Numba JIT) and Rust (Rayon), and validated against NetworkX [12]. Five experiments on an AMD Ryzen 9 3900X (12 cores / 24 threads) produced the following findings.

\textbf{Finding 1:} Naive Python implementations are misleading. Without graph contraction and JIT compilation, Bor\r{u}vka appears 6.6$\times$ slower than Kruskal [3]. With both optimizations, Bor\r{u}vka matches or exceeds Kruskal's sequential performance [2,3,4].

\textbf{Finding 2:} Graph contraction is essential for Bor\r{u}vka [4]. Without it, every round scans all $E$ edges. With it, the edge set shrinks exponentially, reducing total work by a factor of $\log V$ [4,6].

\textbf{Finding 3:} The full Amazon co-purchase network (262K nodes, 900K edges) completes in 0.057s (Python/Numba) and 0.063s (Rust) [3,9], confirming that the algorithm scales to real-world datasets when properly implemented [4,6].

\textbf{Finding 4:} Parallel speedup is limited by the large serial fraction ($f \approx 0.44$ by Amdahl's Law). The sequential find-minimum and merge phases prevent speedup beyond $\sim$2$\times$ even on 12 cores. Rust/Rayon achieves 1.94$\times$ peak vs.\ Python/Numba's 1.35$\times$ due to lower thread-management overhead [4,10,11].

\textbf{Finding 5:} Numba JIT achieves within 0--50\% of native Rust performance for Bor\r{u}vka's compute-bound loops, but Rust maintains a consistent $\sim$2$\times$ advantage for sort-dominated algorithms (Kruskal) due to superior \texttt{sort\_unstable} (pdqsort) [10,11].

\textbf{Recommendation:} Use Kruskal's for quick sequential prototyping [2]. For parallel production systems, use Bor\r{u}vka with graph contraction and a lock-free concurrent Union-Find to reduce the serial fraction [4,6,8]. Compile with Numba for rapid development or Rust/C++ for maximum throughput [10,11].
